### 1.1 `user_version` 4 を 5.6.0 に割り当てる根拠

現在値は **3**（`queen_store.rs` の migration 到達点 3 経路とも `PRAGMA user_version = 3`）。
A-6 の retention は**消費していない**（コード内コメントが「4 の採番は 5.6.0 と 6.0.0 の間で未決のまま」
と明記）。`queen_store.rs` は **`version > 3` の DB を開かずにエラーにする**ので、一度でも 4 を書いた
ビルドがユーザーの `queen.sqlite3` に触れると**それ以前の全ビルドがそのファイルを開けなくなる**。
ダウングレード経路も自動修復も無い。**番号を持っていくのは「先に出荷したほう」であり、ドキュメントの
予約は 4 番を取り返せない。**

5.6.0 に与える理由:

- **5.6.0 だけが既存データの移行を伴う**。`workflow_runs` は 5.0.1 から本番データが入っている唯一の
  対象で、`steps_json` を step 行へ展開する破壊的 migration が要る。6.0.0 の 3 表（`replays` /
  `secrets_audit` / `sandbox_events`）と 5.5.1 の `spans` は**既存データゼロの純追加**で、番号の前後で
  難易度が変わらない。難しいほうに小さい番号を先に取らせるほうが、`BEGIN IMMEDIATE` 一括 /
  `IF NOT EXISTS` / ROLLBACK という migration の定型を素直に適用できる。
- **6.0.x は着手が最も遠い**（plan.md §3 P6 の着手順で 5 番目。`sandbox.rs` / `secrets.rs` /
  `replay.rs` はいずれもソースが存在しない）。5.6.0 は A-6 完了で今日から着手できる。

**請求者は 2 者ではなく 3 者だった**（本整理での発見）。`spec-phase5-5.md` §3.4 の **`spans` 表**
（5.5.1 OTel）が、plan.md §5.1 にも next-implementation §4.2 にも登場していない。
`observability.enabled: false` が既定なので「有効化時に `CREATE TABLE IF NOT EXISTS` するだけで
bump しない」という設計も選べるが、それは version 検証を無意味化する（**同じ 3 でもスキーマが 2 通り
存在する**）ので採らない。素直に bump し、出荷順で番号を取る。
plan.md §5.1 の注は memory 系テーブルについても「v3 内 additive か v4 を切るかを着手時に決め直す
必要がある」と書いており、**潜在的には 4 人目**がいる。

**規約そのものを書き換える。** plan.md §5.1 を「**Phase 単位の予約表**」から
「**出荷実績表 + 次の空き番号 1 つ**」へ変える。`queen_store.rs` の挙動（未来の番号を開かない）は
「番号 = 出荷順の単調台帳」を強制しており、**Phase 単位の予約と原理的に噛み合わない**。
噛み合わない規約を維持していたことが、この衝突を生んだ原因そのものである。

## 2. v0.5.9 に入れるコード（S サイズ 3 件 + 掃除）

新機能は 1 つも足さない。入れるのは次だけ。

### 2.1 終端した run の kickoff を ack する（A-5 の入口を広げる）

**症状**: `retire_run_kickoffs` の呼び出し元は cancel と abandon の **2 か所だけ**（実測）。
`joinOn: reply` でない step は route 1（PTY exit）/ route 2（semantic done）で完了するので
**返信が無く kickoff は未 ack で残る = 滞留するほうが多数派**。A-6 の retention は `workflow_runs` を
DELETE するだけで `inbox_messages` に SQL を投げないので効かない。

**行き着く先**: `inbox_messages` が `MAX_MESSAGES_PER_PROJECT = 50,000` に達すると `enforce_limit` が
**削除ではなく `Err` を返す** = `send_inbox` が拒否される。すると `deliver_kickoff` が失敗し、
`joinOn: reply` の step は `Failed`、かつ `attach_kickoff_result` の KNOWN LIMITATION どおり
**spawn 済みのペインは閉じられず孤児化**する。`joinOn: reply` でない step は best-effort なので
**ペインは立つが指示が届かない（無言のペインが 1 枚）**。

**なぜ今か**: 5.0.8 `schedule:` の出荷で、この表への流入が**無人化した**。しかも症状（無言のペイン /
孤児ペイン）から原因（inbox 満杯）に辿り着ける導線が無い。**数か月後に「workflow が突然動かなくなる」
形で顕在化する時限爆弾**である。

**直し方**: `retire_run_kickoffs`（既存の純関数）を `Succeeded` / `Failed` の終端書き込みでも呼ぶ。
**未実測**: 50,000 到達までの実時間。毎時 1 run × kickoff 3 step なら 72 行/日で約 690 日という算数は
できるが、返信ぶんが加算されるので実測が要る（U19 (4) のついでに `inbox_messages` の行数も測ること）。

### 2.2 `send_os` を detached thread へ出す

**症状**: `escalated` は **step（コピー）単位**のフラグなので、`onEach` のコピーが同一 tick で一斉に
枯渇すると **1 tick で最大 64 通**（上限は `STREAM_MAX_UNITS = 64`）。`notifications.rs` の match は
`ChannelKind::Os => send_os(app, …)` を**そのまま呼ぶ**（detached thread に出るのは webhook 系だけ）
ので、**OS トースト 64 発が 200ms tick を直接ブロックする**。

**なぜ今か**: 踏むのは `onEach`（5.0.7）× `retry`（5.0.4）× `notifications`（4.4.2）を全部使う設定、
つまり**先進ユーザー**。直しは **`send_os` も detached thread に出すだけ**で、1 行で tick ブロックが
消える。run 単位のダイジェスト化（本筋）は spec-notifications v2 送りのままでよい。

CONTRACT 続報16 は「枯渇 1 回につき escalation は 1 通」と書いているが、これは **step 単位**の話で、
run 単位のバーストには触れていない。既知の限界に 1 行足すこと。

### 2.3 run 全体の失敗にも escalation を出す

**症状**: escalation の入口は **step の retry 枯渇 1 つだけ**。`retry:` を書いていない step だけの
workflow は、run が red で終わっても **1 通も出ない**。

**なぜ今か**: `schedule:` で無人起動する workflow の失敗を外に出したければ、**step に `retry:` を
書かねばならない**。これを知らずに `schedule:` を使うと、**スケジューラは失敗を静かに溜める装置に
戻る**。5.0.8 が「載せてよい」と判断された根拠は A-4 の escalation 配線（plan.md §4 項目 10）なので、
ここが埋まっていないと 5.0.8 の前提が半分しか成立していない。

**直し方**: run が `Failed` で終端したときに 1 通出す入口を足す。既存の `notify_escalation` と
`NotifyContext.origin` をそのまま使えるので新しい配送機構は不要。

### 2.4 掃除（コスト実質ゼロ）

- **A-6 の起動時一括掃除**: 現状は「次に run が 1 本終わるまで縮まない」ので、A-6 以前のビルドが
  太らせた DB は、もう run しないプロジェクトなら**永久に残る**。起動時に 1 回呼ぶだけ。
  （`VACUUM` は**見送り** — 起動が遅くなる。空きページの再利用にとどめる）
- **`src-tauri/src/orchestrator.rs.bak` を git から外す**。5.0.0 から追跡されたままで、**v0.5.8 にも
  同梱されている**。ガイド §1 が「commit 済みの `.bak` に旧コードが残るが実行系とは無関係」と
  注記せざるを得なくなっている元凶。
- **CONTRACT.md の「続報11」が 2 つある**（2026-07-30 の計測フィールドと 2026-08-04 の `onEach: reply`）。

## 3. 実機検証の計画

未消化は 14 件（U4 / U6 / U7 / U8 / U10 / U12 / U13 / U14 / U15 / U16 / U17 / U18 / U19 / U20）。
律速は待ち時間ではなく **config を切り替えるたびのアプリ再起動と、実エージェントの応答待ち**
（1 往復 約 4.3 秒 / cold start +3.4 秒、plan.md §6.12 実測）。

### 3.1 バンドル 1 — 1 つの config・1 起動で U4 + U17 + U16（最優先）

3 つとも「kickoff を送る step + 返信するエージェント + Queen の mailbox を数える」という同じ道具立てなので、
**同じ `ptygrid.yml` に 3 本の workflow を並べれば 1 起動で全部見られる**。

- `wf-concurrent`（2 step、`joinOn: reply`）を **2 本同時に ▶** → **U4**（および §4 の検証）
- 同じ workflow を 1 本 ▶ して返信前に ⏹ → 次の run でペインに `list_inbox` を数えさせる → **U17 (1)(2)**。
  2 本同時に流して片方だけ ⏹ → **U17 (4)**
- `wf-merge`（`implement` → `reviewA` / `reviewB` 両方 `handoffTo: verdict` → `verdict`）→ **U16**
- 実行中にアプリを落として再起動 → 「破棄」 → **U17 (3)**。
  **この再起動を U19 (3)（`state='running'` が retention に巻き込まれていないこと）と兼ねられる**

所要 約 70 分。

### 3.2 バンドル 2 — エージェント不要の 2 件（U18 + U19）

どちらも **実エージェントが 1 体も要らない**（`cmd: /bin/false` と `sh -c 'sleep N'` で足りる）。

- `notifications:`（`os` +可能なら Slack webhook、`level` は**既定の `critical` のまま**）を書き、
  `/bin/false` + `retry: {max: 1, backoffMs: 500}` の 1 step workflow → **U18 (1)〜(4)**。
  続けて `level: silent` に変えて → **U18 (5)**。**最重要の観測点は「枯渇の瞬間に 1 通で、200ms ごとの
  連投にならないこと」**（`escalated` フラグの実効）

## 4. 本整理での発見: 並行 run 間でペインが横取りされうる

**plan.md にも CONTRACT.md にも記載が無い。** コード上の経路として確認したが、**実機再現は未実施**。

- `agent_claimed_by_other_step` は **同じ run の outcomes しか見ない**（呼び出し側が `&run.steps`）。
- 一方 `live_session_id` は **`PtyManager` 全体から名前一致で拾う**。
- したがって、同名 workflow の run A と run B が同時に走り、ある step が singular（`copies == 1`）なら、
  **run B の step が run A のペインを adopt して同じ `session_id` を持つ**。
- 完了判定は `session_id` キー（route 1）なので、**そのペインが 1 回 exit すると両方の run の step が
  同時に完了する**。さらに kickoff の recipient は agent 定義名で共有されるので、
  **同じペインが 2 通の kickoff を見る**。

**U4 が暴くはずの挙動そのものである。** U4（同名 workflow の並行 run が互いの返信を取りこぼさないこと）は
v0.5.8 の予定に入っていて未消化のまま残り、その結果この経路は一度も実機で試されていない。
**バンドル 1 で U4 を見るとき、真っ先にこれを確認すること。** 実在が確定したら v0.5.9 で直す
（そのぶんスコープが増える）。

なお、§3 P5 の実タスク測定は「同じ課題を 2 構成で並行に流す」ので、**これが実在すると測定結果そのものが
汚染される**。P5 が U4 を前提にしていた理由がここにある。

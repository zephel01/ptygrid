# review-starter — 3か所埋めれば動くレビュー体制の雛形

## これは何か

エージェント3体に「実装 → レビュー → ジャッジ」を順番にやらせる `ptygrid.yml` の雛形です。
実装役がコードを書いてコミットし、レビュー役がそのコミットの差分を読んで指摘をファイルに書き出し、
ジャッジ役が指摘とコードを突き合わせて ACCEPT / REVISE を判定します。
3体は同じ CLI（既定は `claude`）で、役割の違いはモデルではなく起動時に渡すプロンプトで付けています。
成果物は `~/.ptygrid-review/` の3つのファイル（`changes.md` / `review.md` / `verdict.md`）に残るので、
ワークフローが終わったあとで人間が読み返せます。マージは誰もしません（人間が判断する前提です）。

## 前提

- **Queen MCP を CLI 側に登録しておくこと。** これが一番詰まる箇所です。ptygrid は
  エージェントに指示を渡すのに内蔵の MCP サーバー（Queen）を使うので、CLI 側に Queen が
  登録されていないと、1段目のペインは開くのに指示が受け取れず、何も進みません。
  登録コマンドはツールバー右の **「● Queen :39237」バッジ**をクリックするとトークン込みで
  コピーできます。Claude Code なら次の形です（`<token>` はバッジのコピーで実値になります）。

  ```bash
  claude mcp add -s user --transport http queen "http://127.0.0.1:39237/mcp?token=<token>"
  ```

  **`-s user` を必ず付けてください。** 既定の local スコープは「コマンドを実行したディレクトリ限定」の
  登録になるため、ペインの作業ディレクトリと違う場所で登録すると Queen が見えません。
  登録は初回だけで、トークンは再起動後も有効です。詳細は
  [docs/guide/userguide.md](../../docs/guide/userguide.md) の「Queen のセットアップ」を参照
  （Codex CLI / Grok CLI の登録方法もそこにあります）。

- **作業フォルダが git リポジトリであること。** レビュー役は専用の linked worktree で動くので、
  git リポジトリでないと2段目が起動できません。

- **グリッドを空にしておくこと。** ワークフローは1段につき1ペイン使うので、この雛形は3枚
  使います。結果を見るシェルを1枚開いても4枚で、ペイン上限の9枚には余裕がありますが、
  他の作業のペインが残っていると枠待ちになります。開始前に不要なペインは閉じてください。
  なおこの雛形は `autostart` をすべて `false` にしてあるので、読み込んだだけではペインは
  増えません（起動フォルダの「信頼」確認も出ません）。

## 埋める3か所

`ptygrid.yml` の中の `# ▼▼▼ ここを書き換える (n/3) ▼▼▼` と `# ▲▲▲ ここまで ▲▲▲` に挟まれた
`kickoff:` の `TODO:` の行を、自分の依頼内容に置き換えます。**書き換えるのはこの3か所だけ**で、
返信の作法・mailbox 名・ツール名・worktree・タイムアウト・ファイルの受け渡しはすべて埋まっています。

なお `kickoff:` の中で `${VAR}` と書いても環境変数には展開されません（展開されるのは
`agents[].env` の値だけです）。差し替えは YAML を直接編集してください。

### (1/3) implement — 実装役に何をさせるか

対象と完了条件を具体的に書くほど安定します。

> `src-tauri/src/config.rs` の `validate_workflows` に、`timeoutMs` が 100 未満のときに
> エラーを返すチェックを足してください。既存のエラーメッセージの書式に合わせること。
> 同じファイルの `#[cfg(test)]` に、境界値（99 は失敗・100 は成功）のテストを追加し、
> `cargo test` が通ることを確認してからコミットしてください。

### (2/3) review — レビュー役に何をチェックさせるか

観点を並べます。「よしなに見て」だと指摘が散ります。

> 次の観点でレビューしてください。(a) 追加されたチェックが仕様どおりの境界値で動くか、
> (b) 既存のバリデーションと重複・矛盾していないか、(c) エラーメッセージが他の項目と
> 同じ書式か、(d) 追加テストが本当に落ちる条件を踏んでいるか。

### (3/3) judge — ジャッジ役が何を基準に可否を決めるか

ACCEPT の条件と REVISE の条件を、迷わない粒度で書きます。

> ACCEPT の条件は次のすべてを満たすこと: `cargo test` が緑、レビューの指摘のうち
> 「バグ」に分類されるものが0件、既存の公開関数のシグネチャを変えていないこと。
> 1つでも欠けていれば REVISE にし、reason に欠けている条件を書いてください。

## 動かし方

1. このフォルダをそのまま使うか、`ptygrid.yml` を自分のプロジェクトルートにコピーします。
2. 上の3か所を埋めて保存します。
3. ツールバー左の**作業フォルダ**欄にそのフォルダを入れて「読み込み」を押します。
   読み込みに失敗する場合は YAML の構文エラーなので、出たメッセージを直します。
4. 左のドックの **Workflows** タブを開き、`review-loop` の **▶ Run** を押します。
5. 1段目のペインが開いて実装が始まります。各段は担当エージェントが `reply_inbox` で
   返信した時点で完了し、次の段が開きます。
6. 終わったら `~/.ptygrid-review/verdict.md` を読みます。

レビュー役の worktree は実行のたびに `ptygrid/reviewer/<連番>` という新しいブランチ付きで作られ、
自動では消えません。溜まってきたら `git worktree list` で確認して
`git worktree remove --force <パス>` で掃除してください。

## うまくいかないときの症状と原因

**1段目のペインは開いたのに何も始まらない / ペインに「そんなツールは無い」旨が出る**
→ Queen MCP が未登録か、`-s user` を付けずに登録したせいでそのディレクトリから見えていません。
`claude mcp list` に `queen` が出るか確認してください。出ていなければ上の登録コマンドをやり直します。
この状態だと step は `timeoutMs`（1段目は60分）まで `Running` のままです。

**レビュー役が「差分が無い」と言う / `review.md` が空**
→ 実装役がコミットしていないか、作業を終える前に `reply_inbox` を呼んでしまっています。
段の完了判定は**最初の返信**で決まるので、「了解しました」を先に返すとその時点で次の段が始まります。
実装役のペインを見て、コミットが積まれているか（`git log`）を確認してください。

**書いたはずの `dependsOn` や `joinOn` が効かない / 全部の段が同時に走る**
→ キーの綴り間違いです。ワークフローのキーは camelCase（`dependsOn` / `joinOn` / `timeoutMs` /
`onFailure` / `fanOut`）で、綴りの違うキーは**エラーにならず黙って無視され**、既定値で動きます。
`depends_on` と書くと依存が無いことになり、その段は最初から実行可能な根として即座に開きます。

**次の段が `Pending` のまま開かない**
→ 依存待ちかペイン枠待ちのどちらかです。step の `error` に
`waiting for a free pane slot (N/9 occupied)` と入っていれば枠待ちなので、要らないペインを閉じます。
5分待っても空かないとその step は失敗します。
